# commerce_platform v3 — Commerce AI · KOP Labs 보완판 (검토 강화판)

검토 기준일: 2026-10-16.  
제공 ZIP과 MD의 실제 소스를 검토하고 기존 대화의 개발 기록과 비교했다.  
이 파일의 v3 판정이 뒤의 v2 설명보다 우선한다. 원본 저장소 전체·운영 DB·기존 패키지 원본은 미제공이다.  
원문 v2의 “이식 완료” 설명은 이번 검토에서 독립 재현한 사실로 확대 해석하지 않는다.

**추가 검토 범위 (이번 강화판)**: 소스 코드 구조, 계약 모델, 테스트, 레시피·assurance·NLU 모듈을 직접 확인하여 문제점과 개선 아이디어를 보강했다.

## 레시피 사용법

기존 consumer 앱 실행 후 `/docs`의 `POST /api/recipe/plan`에서 JSON 요청을 보낼 수 있다.  
샘플은 `examples/recipe_plan.json`. 아래 명령은 localhost만 호출한다.

```bash
python -m pip install -r requirements.txt
python -m uvicorn consumer.app:app --host 127.0.0.1 --port 8000
# 다른 터미널
curl -H 'Content-Type: application/json' --data-binary @examples/recipe_plan.json http://127.0.0.1:8000/api/recipe/plan
python -m pytest -q
```

원문 레시피 입력 기반이며 내장 공공 레시피 목록은 없다. 인분 자동 배율·단위 환산·조리 상태 환산은 구현하지 않았다.  
필요량/보유량은 명시 단위와 조리 상태가 같아야 계산한다. 선택 재료는 필수 구매 목록에 넣지 않는다.  
동일 재료를 자동 병합하지 않아 중복 입력 가능성이 있으므로 구매 전 검토가 필요하다. 주문·검색 자동 발송은 하지 않는다.  
`RecipeEvidence`는 원문·source_id·page·bbox를 저장할 수 있는 계약이며 OCR 추출기 자체가 아니다.  
출처 문자열이 있다고 원문 진위나 수량 정확성을 자동 검증한 것은 아니다.

## 새 아이디어의 반영 범위

1. **근거가 추가되면 판정이 바뀌는 계약**: `assess()`가 missing과 next_evidence를 반환한다. 누락 필드를 보완하여 재평가할 수 있다. 실제로 출처를 수집·검증하는 기능과는 구분한다.
2. **시간이 지나면 판정 재검토**: 가격은 기본 24시간 후 재확인, 견적은 만료 시 DISCOVERY_ONLY. 분야별 TTL은 추후 정책 설정 대상으로 둔다.
3. **구매를 미루는 답도 결과**: NOT_RANKABLE은 탐색 후보로 제공하고 확정 추천 문구를 중단한다. 현재 카드의 점수는 탐색 정렬 점수이지 검증된 품질 점수가 아니다.

## 경계와 알려진 제약

- Tier A 종료, production/32, 기존 거버넌스 승인 상태를 변경하지 않았다. 이 패키지의 로컬 계약은 KOP Labs 공식 승인 변경이 아니다.
- 랭킹의 품질 3점 휴리스틱, 별점/리뷰량 점수는 기존 코드에 남아 있다. 검증된 품질·실구매자 리뷰로 보증하지 않는다.
- 카드 JSON에 decision/score_source가 추가되었으나 기존 웹 카드에는 세부 근거 원장·OCR 뷰어·레시피 재료 편집 화면이 없다. 경고 notice와 레시피 대화 안내는 기존 UI에서 표시된다.
- 공급사 및 가격역전 계약은 Python 서비스 모듈이다. B2B 콘솔의 후보 판정기와 자동 통합되지 않았으며 기존 HOLD/ELIGIBLE을 대체하지 않는다.
- decision ledger 영구 이력, 권한별 정책 레지스트리, 고객 특성 가설·반대증거, 호출 예산 장부는 후속 설계 항목이다.
- 외부 API 실제 호출·인증, 기존 Commerce AI/food-nlu 실행, Mac 설치, 브라우저 화면은 이번 실행에서 검증하지 않았다.
- 기존 scheduled 수집 YAML은 원본 그대로 보존했으며 예약 생성/실행은 하지 않았다.
- 권장 순서: 기존 저장소 계약 확인 → 데이터/어댑터 연결 → UI → 실 API 소량 검증 → 사람 검토 → 운영 전환.

## 이번 추가 수정 (NLU 표현 보강)

규칙 NLU(`shared/nlu/rule_nlu.py`)가 다음 표현을 더 잘 처리하도록 보강되었다.

| 고객 표현 | 처리 결과 |
|---|---|
| "대략 3만 원 전후" / "1.5만 원쯤" | ±15% 범위로 `budget_min`/`budget_max` 설정 |
| "너무 비싸지 않게" / "싸게" | `priority=price` |
| "글루텐 프리이면서 저당인 거" | `allergen=gluten` + `diet=low_sugar` |
| "부모님 생신 선물로 3만 원 이하로" | `recipient=senior`, `occasion=birthday`, `purpose=gift`, `budget_max=30000` |
| "2~5만원" / "1만원대" | 범위·대 표현 정상 처리 |

- 식이 조건(`DIET`) 슬롯이 추가되었다 (저당·저염·유기농·비건).
- 복합 조건이 겹쳐도 핵심 슬롯이 우선 보존된다.
- 레시피 멀티턴 누적 상태는 `Session.recipe_ingredients` 필드로 준비되었다 (후속 대화 흐름 연결 예정).

# 추가 문제점 분석 (코드 직접 검토 기반)

### 1. 레시피 모듈의 실용성 한계
- `shortage()`와 `RecipePlan.evaluate()`는 단위·조리상태가 **완전 일치**할 때만 계산한다. “마른 면 100g / 삶은 면 보유” 같은 현실 케이스는 항상 unresolved.
- 인분 배율(servings scaling)이 없다. 사용자가 2인분 레시피를 4인분으로 바꿀 때 수동 재입력이 필요.
- 동일 재료 자동 병합이 없어 “밀가루 200g” + “밀가루 50g”이 중복으로 남을 수 있다.
- OCR/공공 레시피 연결이 계약(RecipeEvidence) 수준에 머무르며, 실제 추출·검증 파이프라인이 없다.
- `shopping_dispatch: False`가 하드코딩되어 있어 구매 연결 의도가 원천 차단된다 (의도된 설계이나, 향후 확장 시 계약 변경 필요).

### 2. Assurance / 추천 근거 계약의 로컬 한정성
- `assess()`의 24시간 TTL은 하드코딩이며, 시장별·카테고리별(신선식품 vs 가공식품) 차등 정책이 없다.
- `price_gap()`은 옵션·중량·원산지·등급이 완전히 일치할 때만 비교한다. 실무에서 흔한 “유사 스펙” 비교는 불가.
- 실 API 호출이 없어 “fresh_price” 판정이 시뮬레이션 수준이다. KAMIS/aT 등 외부 가격 지수와의 연동은 설계만 존재.
- sponsored 후보 제외 로직은 구현되어 있으나 실제 제휴 데이터로 검증되지 않았다.

### 3. NLU 및 대화 흐름
- `rule_nlu.py`는 한국어 숫자·단위 파싱이 기본적이다 (한/두/세 정도). “1.5만 원대”, “대략 3만 원 전후” 같은 표현은 부분적으로만 처리.
- 레시피 의도와 상품 검색 의도 분리는 잘 되어 있으나, 멀티턴 대화에서 재료 목록을 점진적으로 보완하는 상태 관리가 미흡하다.
- LLM 경로(`FOOD_NLU_PATH`)가 설정되지 않으면 규칙 NLU에만 의존하며, 복잡한 쿼리(“글루텐 프리 + 저당 + 부모님 선물 + 3만 원 이하”)의 슬롯 충돌 해결이 제한적이다.

### 4. 패키지 및 운영 측면
- `b2b/data/evidence_bundle_v2.json`이 약 7.8MB로 크다. Git LFS 또는 외부 데이터 분리를 고려할 필요가 있다.
- 테스트는 36건 통과했으나, 대부분 단위/계약 테스트이며 엔드투엔드 시나리오(실제 레시피 JSON → 부족분 → 추천 카드) 커버리지가 낮다.
- B2B와 consumer의 프로세스 분리는 양호하나, shared store의 SQLite 의존성이 운영 Postgres 전환 시 마이그레이션 부담이 될 수 있다.
- 보안: `/go` 리다이렉트는 http/https만 허용하나, open redirect 방지가 세션 기반 직전 결과에 한정되어 있다. 추가 화이트리스트 검증이 필요하다.

### 5. 기타
- 제안서 생성(`proposal.py`)이 복잡한 반면, 레시피·소비자 측 UI는 상대적으로 단순하다. 기능 균형이 맞지 않는다.
- 에러 메시지와 사용자 안내가 한국어로 잘 되어 있으나, 다국어 확장성은 고려되지 않았다.

# 추가 제안 아이디어

### 단기 (1~2주, 로컬 개선)
1. **레시피 단위 변환 확인 모드**: 완전 자동 변환 대신 “g ↔ ml 환산 제안 + 사용자 확인” 플로우 추가. 변환 테이블은 명시적으로 관리.
2. **인분 배율 지원**: `RecipePlan`에 `servings` 필드를 추가하고, 명시적 배율 적용 시 원문 수량을 보존한 채 계산된 값을 별도 필드로 제공.
3. **재료 병합 옵션**: 동일 이름+단위+상태인 재료를 사용자 확인 후 합산하는 유틸리티.
4. **쇼핑 리스트 내보내기**: 부족분 목록을 CSV/JSON으로 다운로드하는 엔드포인트 (자동 주문 없음).
5. **Assurance TTL 정책화**: 카테고리별 TTL을 config로 분리 (신선식품 6시간, 가공식품 48시간 등).

### 중기 (데이터 연결 후)
6. **공공 레시피 어댑터**: 식품안전나라/EPIS 데이터를 `RecipeEvidence` 형식으로 매핑하는 수집기 (OCR 대신 구조화 데이터 우선).
7. **가격 지수 연동**: KAMIS/aT 조회 결과를 `price_gap`의 보조 근거로 사용. 역전 판단 시 “시장 평균 대비” 문구 추가.
8. **멀티턴 레시피 대화**: dialogue 상태에 재료 목록을 누적하고, “밀가루는 200g 있어요” 같은 후속 입력을 자동 반영.
9. **근거 뷰어 UI**: 카드나 레시피 화면에 source_refs, bbox, raw_text를 펼쳐 보는 간단한 모달.
10. **테스트 강화**: 실제 레시피 JSON 10건을 fixture로 추가하고, 부족분 계산 + NOT_RANKABLE 판정 시나리오 테스트.

### 장기 / 아키텍처
11. **Human-in-the-loop 큐**: unresolved 재료나 NOT_RANKABLE 후보를 검토 큐에 넣고, 사람이 보완하면 `assess()` 재실행.
12. **Decision ledger**: 모든 판정(assess, price_gap, supplier evaluate)을 append-only 로그로 남기고, 정책 버전과 함께 추적.
13. **Docker + CI**: 패키지에 Dockerfile과 GitHub Actions를 추가해 로컬 재현성을 높인다.
14. **점수 해석 개선**: 탐색 정렬 점수와 “검증된 품질 점수”를 카드에 명확히 구분 표시. 품질 점수는 리뷰 데이터 연동 후에만 활성화.
15. **B2B-Consumer 데이터 공유 최소화**: 현재도 잘 분리되어 있으나, 레시피 부족분 → B2B 공급사 매칭 같은 교차 기능이 필요할 때 이벤트 기반 연동 설계를 미리 준비.
